hubspec 0.4.0 · hub multi-repo

Um repositório mãe para sistemas multi-repo brownfield

O hub é um repositório Git que descreve um sistema espalhado por vários repositórios. Ele guarda o manifesto dos repos, a documentação gerada a partir do código de cada um, o mapa de dependências e as changes do OpenSpec que atravessam repos. O código continua nos repositórios de origem: o hub trabalha sobre clones locais e entrega o trabalho como uma PR por repo, na ordem de merge.

$ hubspec hub pr add-pix
api: aberta https://github.com/acme/api/pull/1
worker: aberta https://github.com/acme/worker/pull/2
front: pulado — 1 task(s) em aberto: 3.1

Ordem de merge: api → worker

O problema

Num sistema brownfield com vários repositórios, o agente aberto num repo não enxerga os contratos, os eventos e os consumidores que estão nos outros. Uma mudança que atravessa repos vira uma conversa por repo, sem um plano comum, sem ordem de merge e sem uma verificação conjunta. O hub resolve três partes desse problema:

  • Contexto: as docs de cada repo e o mapa de dependências, gerados do código e ancorados num commit, com a desatualização medida contra o remote.
  • Plano único: uma change só no hub, com as tasks agrupadas por repo na ordem de dependência.
  • Entrega coordenada: uma PR por repo, com as PRs irmãs e a ordem de merge, e a verificação dos cenários sobre todos os clones.

Só existe o que já foi feito: uma change criada direto pelo /opsx:propose não tem exploration.md nem decisions.md. Num hub, as tasks começam com [repo] e, depois do hub pr, ganham os links das PRs. Ao arquivar, a pasta inteira vai para openspec/changes/archive/<data>-<nome>/, e as delta specs entram em openspec/specs/. Os arquivos da verificação estão em Arquivos.

Garantias

  • A varredura só lê. O hub document lê arquivos dos clones e nunca executa nada neles.
  • Trabalho local não se perde. O hub sync pula clones com mudanças não commitadas ou com commits que não estão em nenhum remote, e só atualiza com pull --ff-only.
  • Nada fora do hub é apagado. O hub remove só apaga um clone que está dentro da pasta do hub, e recusa um clone com trabalho não enviado sem --force.
  • Commits nos clones só pelo hub pr, numa branch com o nome da change. A branch de trabalho de um repo (main, ou develop num Git Flow) nunca recebe commit do hubspec.
  • Sem prompt de credenciais. O Git roda com GIT_TERMINAL_PROMPT=0 e o gh com GH_PROMPT_DISABLED=1: a autenticação é a da máquina (chave SSH ou gh).
  • Docs ancoradas num commit. O .meta.json de cada repo guarda o commit documentado, e o hub status compara esse commit com a branch do repo no remote.
  • Repos novos não nascem do hub. Criar um repositório é uma task [manual], que bloqueia a change até alguém criá-lo pela automação da organização.
  • Idempotência. hub init, add, depends, document, pr e remove podem ser rodados de novo.

Instalação

O hubspec já traz o OpenSpec dentro e não instala dependências. Há duas formas de distribuição.

Ainda não está no npm

npm i -g hubspec e npx hubspec não instalam este projeto. Não use esses comandos: o nome está livre no npm, e eles instalariam outro pacote se alguém o registrasse.

FormaPrecisa para rodarTamanho
CLI em Node: dist/cli.js, um arquivo com o OpenSpec e as bibliotecas dentroNode 22.12+~2 MB
Binário standalone: um executável por plataforma, com schemas e skills embutidosnada~100 MB

O Bun só é preciso para gerar os dois a partir do código.

CLI em Node

git clone https://github.com/rafaelpolli/hubspec.git ~/hubspec
cd ~/hubspec
bun install                 # só as ferramentas de build (devDependencies)
bun run build               # gera dist/cli.js
mkdir -p ~/.local/bin
ln -sf ~/hubspec/dist/cli.js ~/.local/bin/hubspec
hubspec --version           # 0.4.0

~/.local/bin precisa estar no PATH. Com o npm instalado, npm install -g . dentro de ~/hubspec faz o mesmo que o link. Para atualizar: cd ~/hubspec && git pull && bun install && bun run build, e depois hubspec update em cada projeto e em cada hub.

Binário standalone

cd ~/hubspec
bun run build:bin                                          # dist-bin/hubspec-<plataforma desta máquina>
install -m 755 dist-bin/hubspec-linux-x64 ~/.local/bin/hubspec
bun scripts/build.ts --binary linux-arm64 darwin-arm64 windows-x64   # outras plataformas

Alvos: linux-x64, linux-arm64, linux-x64-musl, linux-arm64-musl, darwin-x64, darwin-arm64, windows-x64, windows-arm64. Só o linux-x64 foi testado. O binário extrai os schemas e as skills em ~/.local/share/hubspec/binary-files/<hash>/ no primeiro uso.

Exemplo ponta a ponta

Um sistema de pagamentos em três repos, num Git Flow, do repositório mãe vazio até a change arquivada e as docs atualizadas.

Sobre a execução

Os comandos e as saídas são de uma execução real. Nela, remotes Git locais fizeram o papel do GitHub, o gh de teste do projeto abriu as PRs, e os merges foram feitos direto nos remotes, como o GitHub faria. As URLs foram trocadas pelas do GitHub. A parte do agente (o texto das docs, a conversa, as decisões, os artefatos e o código) foi escrita seguindo as skills, e aparece aqui como os arquivos que ela produz. As conversas são ilustrativas.

1. O repositório mãe

Quem faz: você

O hub é um repositório comum, criado vazio. Ele guarda a descrição do sistema; o código dos repos nunca entra nele.

gh repo create acme/pagamentos-hub --private --clone
cd pagamentos-hub

A lista dos repos é um texto qualquer, com um repo por linha. Aqui ela fica fora do hub:

../repos.md
# Sistema de pagamentos

- git@github.com:acme/api.git
- git@github.com:acme/worker.git
- git@github.com:acme/front.git

A lista só tem os endereços. Ela não diz o que cada repo faz nem quem depende de quem: as descrições e as dependências entram no repos.yaml no passo 3, quando o agente lê o código. Uma descrição depois do endereço (- git@github.com:acme/api.git — API de pagamentos) também seria aceita, e o agente não a trocaria.

4. Explorar

Quem faz: você agente

Você pede: "quero explorar como aceitar Pix". A skill hubspec-explore roda hubspec list --json e hubspec list --specs --json, que vêm vazios num hub novo (o que o agente lê). Ela lê o system-overview.md e as docs da api e do worker, e conversa com você:

Você

Agente

O banco notifica o Pix pelo mesmo webhook? E quem confirma o pagamento: a api, direto, ou o worker, como no boleto?

Você

Mesmo webhook, com tipo: "pix". Quem confirma é o worker.

Agente

Decidido: o Pix entra pelo webhook atual, com tipo: "pix".
Decidido: o worker confirma, como no boleto.

O genérico muda o BoletoPago, que o worker já consome (docs/repos/worker/interfaces.md). Recomendo o novo. O front não precisa mudar para o Pix ser confirmado: a tela do QR code pode ser uma change própria.

# Exploração: Pix no sistema de pagamentos

- Origem da change `add-pix`, criada em 2026-11-07.

## Decisões

- **Por onde o Pix entra no sistema?** Pelo mesmo webhook do banco (`POST /webhooks/banco`), com `tipo: "pix"`.
- **Quem confirma o pagamento?** O worker, como no boleto: a api só publica o evento.
- **Evento novo ou genérico?** Um evento novo, `PixRecebido { txid, valor }`, no tópico `pagamentos`.

## Resumo da conversa

O fluxo do boleto (banco → api → tópico `pagamentos` → worker) serve de modelo. Foi considerado um evento genérico `PagamentoRecebido` para boleto e Pix, descartado para não mudar o `BoletoPago`, que o worker já consome. O front não muda nesta change: a tela de QR code fica para uma change própria.

A sugestão de deixar o front de fora foi do agente. Por isso ela aparece no resumo, e não nas decisões.

O manifesto é validado a cada comando, antes de qualquer efeito. Os erros dizem o caminho do campo:

Como o hubspec escreve o arquivo

O hub add, depends, archive, remove e add --new reescrevem o arquivo inteiro a partir do modelo validado:

  • o cabeçalho de duas linhas é fixo; outros comentários e campos desconhecidos não são preservados;
  • path é sempre gravado, mesmo quando é o padrão;
  • uma dependência sem via e com origem manual é gravada só como o nome (- api); com via, ou com source: llm, como objeto;
  • a ordem dos repos é mantida.

Editar à mão é suportado. Para não perder comentários, prefira os comandos. O mapa do system-overview.md é regenerado no próximo hub add, depends, archive, remove, document ou init.

Nome e URL

  • Nome: o último segmento da URL, sem .git (git@github.com:acme/api.git → api). Se não der um nome válido, use --name.
  • dono/repo vira git@github.com:dono/repo.git quando gh config get git_protocol -h github.com responde ssh, e https://github.com/dono/repo.git nos outros casos, inclusive sem o gh.
  • URLs completas são gravadas como foram informadas.
  • Mesmo nome, outra URL: erro (já existe um repo api com outra URL (…): use --name). Mesmo nome e mesma URL: o hub add só atualiza os campos informados.

Ordem de dependência

Onde o hub precisa de uma ordem entre repos (a ordem de merge do hub pr), ele usa o algoritmo de Kahn sobre dependsOn:

  • só contam as dependências entre os repos do conjunto; autodependência é ignorada;
  • a cada passo, sai o primeiro repo, na ordem de entrada, sem dependências pendentes;
  • num ciclo, os repos que restam saem na ordem de entrada, sem erro.

No hub pr, a ordem de entrada é a ordem em que os repos aparecem no tasks.md, e as dependências são as do manifesto mais as que a change declara (detalhes).

  • O caminho de cada clone vem do path do manifesto (padrão workspace/<name>). Um path absoluto aponta para fora do hub; nesse caso, o hub remove nunca apaga a pasta.
  • O hub init acrescenta ao .gitignore a linha workspace/, com um comentário, se ela ainda não existir.
  • Um repo arquivado deixa de ser sincronizado, mas o clone dele fica no disco até você apagá-lo.

A branch de trabalho

A branch de trabalho de um repo é a mesma em todas as operações:

ComandoUso da branch
hub synca branch clonada, atualizada e para onde o clone volta
hub documenta branch documentada; recusa um clone em outra branch ou atrás de origin/<branch>
hub statusa referência: as docs são comparadas com origin/<branch>
hub pra base das PRs (gh pr create --base <branch>)

Ela é resolvida nesta ordem:

  1. a branch do próprio repo no repos.yaml, gravada pelo --branch do hub add ou à mão;
  2. a branch do topo do repos.yaml, a branch de trabalho do hub, gravada pelo hub init --branch;
  3. no registro de um repo num hub sem branch, a branch padrão do remote, lida com git ls-remote --symref <url> HEAD e gravada no repo. Um repo cuja branch padrão no GitHub já é develop fica com develop. Se o remote não responder, o valor é main.

A lista do --repos-file não indica a branch: para uma exceção, use hub add <url> --branch depois do init.

Qual branch usar

Use a branch de integração, isto é, a que recebe as PRs. As docs servem para planejar a próxima change, e toda change sai dessa branch e volta para ela.

Fluxo do timeBranchPor quê
GitHub Flow, trunk-basedmainé onde as PRs entram e de onde as changes saem
GitFlowdevelopcom main, as docs não mostrariam o que já foi integrado em develop, o agente planejaria sobre código antigo e as PRs iriam para a main

Com develop, as docs descrevem código que ainda não está em produção. Como a mesma branch serve às docs e às PRs, não dá para documentar main e abrir PRs para develop.

Git Flow: a branch do hub

Num Git Flow, as PRs de feature vão para develop, as de release para homologação e só elas chegam à main. O hub trabalha na primeira etapa: informe develop como a branch de trabalho do hub.

  • Conferência no registro. Um repo que segue a branch do hub é conferido com git ls-remote <url> refs/heads/<branch>, no lugar da consulta à branch padrão. Sem a branch no remote, o registro acontece e o init avisa. Se o remote não responder, não há aviso. Um --branch explícito não é conferido.
  • Sem fallback para a main. Um repo sem develop não passa para a branch padrão sozinho: num Git Flow, isso mandaria PRs para produção. O sync falha nele com o remote não tem a branch develop até a branch existir ou o repo ganhar a sua.
  • Mudar a branch do hub muda todos os repos que a seguem. Edite o branch do topo, ou rode o init --branch de novo.
  • O nome é validado com git check-ref-format --branch, no init e no add.
  • Fora do hub. As PRs de release e de produção, e o fluxo do próprio repositório do hub, ficam com o time. O hubspec não faz commit no hub.

Autenticação

  • Todo Git do hub roda com GIT_TERMINAL_PROMPT=0: sem credencial configurada, o comando falha em vez de esperar uma senha.
  • Use a autenticação da máquina: uma chave SSH para URLs git@github.com:…, ou o gh como credential helper para HTTPS (gh auth setup-git).
  • O gh é usado só no hub pr e para escolher o protocolo de um dono/repo.

Trabalho nos clones

  • O apply implementa as tasks direto nos clones, sem commit. O hub pr leva essas mudanças para a branch da change e faz o commit.
  • Enquanto houver mudanças não commitadas num clone, o sync não mexe nele. É seguro rodar o sync no meio de uma change.
  • O hub document avisa quando o clone tem mudanças não commitadas: a varredura as vê, mas o commit registrado no .meta.json não as tem.

As dependências entre os repos

Você não informa as dependências entre os repos: nem o --repos-file nem o hub init as leem. Quem as grava no repos.yaml é o agente, enquanto preenche as seções, a partir do código:

O agente procuraExemplo de --via

Para cada uma, ele roda hubspec hub depends <repo> --add <outro> --via "…" --source llm, que grava a dependência e regenera o mapa.

  • Só o agente faz isso. Rodado no terminal, o hub document só varre os repos e cria os templates. Os manifestos que a varredura lê dão as dependências de pacotes (npm, pip…), não as que existem entre os repos do hub.
  • É uma inferência. O agente vê o que está no código e pode deixar passar uma dependência que só existe na configuração de produção. As que ele encontrou aparecem com ¹ no mapa, para você conferir.
  • O --done não confere as dependências. Ele aceita um repos.yaml sem nenhuma, o que também é o certo quando os repos não dependem uns dos outros.
  • As que faltarem, você registra com hub depends ou hub add --depends. Elas ficam com source: manual, e o agente pergunta antes de removê-las.
  • Ao atualizar as docs, o agente refaz esse passo: acrescenta as dependências novas e tira as que sumiram do código (atualização incremental).

A descrição dos repos

A coluna "Descrição" do mapa vem da description de cada repo no repos.yaml. Ela chega lá de três formas:

  • o resto da linha do repo no --repos-file, no hub init;
  • um hub add <url> --description "…" rodado por você;
  • o agente, ao documentar, para os repos ativos que estão sem descrição. Ele escreve uma frase sobre o que o repo faz, tirada do "Propósito" do overview.md, e roda hub add <url> --name <repo> --description "…". Num repo já registrado, o comando só troca a descrição.

O agente não muda uma descrição que já existe, porque ela pode ter sido escrita por você. Se ela contradiz o código, ele aponta isso no resumo final. Ele também não roda o comando para um repo arquivado, porque o hub add o reativaria. As descrições que ele gravou aparecem no resumo, para você revisar.

Desatualização: hub status

Para cada repo do manifesto:

  1. arquivado → arquivado; sem clone → não clonado;
  2. git fetch origin <branch>. Sem acesso ao remote, usa o último origin/<branch> conhecido e avisa;
  3. sem .meta.json → sem docs;
  4. commit do .meta.json igual a origin/<branch> → em dia; diferente → desatualizada, com a contagem de commits entre os dois.

A comparação é com o remote, não com o clone. Por isso, o merge de uma PR aparece no status antes de qualquer sync, mesmo com o clone ainda na branch da change:

$ hubspec hub status
api: desatualizada — documentado e3b6c89c3326, atual 056e63141380 (1 commit(s) depois)
  o clone está na branch add-pix
  rode `hubspec hub sync` antes de documentar
worker: em dia
  o clone está na branch add-pix
  rode `hubspec hub sync` antes de documentar
front: em dia

Atualize com: hubspec hub document api

A saída é 1 quando algum repo está desatualizada ou sem docs, o que permite usar o comando num job agendado que falha quando a documentação precisa de atenção. não clonado e arquivado não mudam a saída.

Atualização incremental

Num repo que já tinha docs, a hubspec-document atualiza só o que o código novo mudou:

  1. hubspec hub sync e hubspec hub document <repo>, que gera um .scan.json novo e mantém os textos;
  2. o agente compara o commit do .scan.json com o do .meta.json, olha git -C workspace/<repo> log --stat <antigo>..HEAD e edita as seções afetadas;
  3. ajusta as dependências com hub depends (remove as que sumiram do código; as manual só com a sua confirmação);
  4. hubspec hub document --done <repo>.

Limites

  • Só leitura. Durante a conversa, o agente não escreve arquivos e não roda comandos que mudam algo. Por isso, não roda hub sync, hub document nem hub depends. Se faltar um clone ou uma doc, ele pede que você rode o comando. Na exploração, essa regra vale acima do AGENTS.md, que manda rodar o sync quando falta um clone.
  • Docs em dia. Na dúvida, o agente roda o hub status, que só consulta. Se a doc de um repo estiver desatualizada, ele avisa antes de se apoiar nela. As docs descrevem a branch de trabalho (num Git Flow, develop), então incluem o que já foi integrado e ainda não está em produção (qual branch usar).
  • Decidido e sugerido ficam separados. Quando você decide algo, o agente repete a decisão numa linha ("Decidido: …"). O que ele só sugeriu não entra no handoff como decisão.
  • A change não nasce sozinha. O agente pode dizer que a ideia está madura, mas só cria a change quando você pede.

Virar change

Quando você pede "vira change", acontecem quatro passos, nesta ordem:

Changes multi-repo

Uma mudança no sistema é uma change só, em openspec/changes/<change>/ do hub, com as tasks agrupadas por repo na ordem de dependência. O formato do tasks.md é o contrato entre o agente, que escreve, e o hub pr, que lê.

Onde fica

Os artefatos são os do OpenSpec (proposal.md, specs/, design.md, tasks.md), mais os do hubspec (exploration.md, decisions.md, .hubspec/, verification.md). O fluxo é o de sempre (explore → decide → propose → apply → verify → archive). No hub, a hubspec-explore e a hubspec-decide leem o system-overview.md e as docs dos repos antes do código; uma decisão típica é em quais repos a mudança acontece e em que ordem.

seção   := "## " [N "."] título
título  := repo | "Manual" | repo " (depende de: " repo {", " repo} ")"
task    := ("-" | "*") " [" (" " | "x" | "X") "] " [id " "] ["[" tag "] "] texto [" → PR: " url]
id      := N {"." N}
tag     := repo | "manual"
repo    := um name do repos.yaml
  • Só títulos de nível 2 (## ) abrem uma seção.
  • O repo de uma task é a [tag] no começo do texto. Sem tag, é o título da seção, se ele for exatamente um name do manifesto ou Manual (sem diferenciar maiúsculas).
  • (depends on: …) também é aceito no lugar de (depende de: …).
  • O sufixo → PR: <url> é escrito pelo hub pr; um sufixo existente é substituído.
  • As regras do hub pedem a tag em toda task, e o caminho ou componente alvo no fim do texto.
openspec/changes/add-pix/tasks.md
## 1. api

- [x] 1.1 [api] Publicar o evento PixRecebido — `src/events.ts`

## 2. worker (depende de: api)

- [x] 2.1 [worker] Consumir PixRecebido e confirmar o pagamento — `internal/pix/`

## 3. front

- [ ] 3.1 [front] Tela do QR code — `src/Pix.tsx`

A ordem das seções é a ordem de execução: primeiro quem os outros consomem (contrato, lib, API). Uma dependência que a change cria e que ainda não está no manifesto vai no título da seção; o hub pr a soma às do repos.yaml para a ordem de merge.

Regras injetadas no OpenSpec

O hub init grava as regras do hub no openspec/config.yaml. O OpenSpec entrega esses campos ao agente pelo hubspec instructions, que o /opsx:propose e o /opsx:apply padrão consultam. Por isso, as regras valem em qualquer ferramenta, mesmo sem as skills do hubspec.

openspec/config.yaml (parte do hub)
context: |
  <!-- hubspec:inicio -->
  Este repositório é o hub de um sistema multi-repo: repos.yaml lista os repositórios, docs/ tem a documentação deles e o código fica nos clones em workspace/<repo>/. Siga o AGENTS.md da raiz.
  - Antes de propor ou implementar, leia docs/system-overview.md e depois docs/repos/<repo>/ dos repos envolvidos; abra o código em workspace/<repo>/ só quando a doc não bastar.
  - Uma mudança que atravessa repos é uma change só, aqui no hub.
  - No apply, implemente cada task dentro de workspace/<repo>/ do repo indicado, na ordem do tasks.md; não comece nada enquanto houver uma task [manual] aberta antes.
  - Num repo com template: true no repos.yaml, siga a estrutura do template e não a recrie.
  <!-- hubspec:fim -->
rules:
  proposal:
    - "Hub: diga em quais repos do repos.yaml a mudança acontece e o que muda em cada um."
  tasks:
    - "Hub: toda task começa com o repo entre colchetes, um nome do repos.yaml, ou com [manual], e termina com o componente ou caminho alvo, …"
    - "Hub: agrupe as tasks por repo, uma seção por repo (## 2. api), na ordem de dependência: …"
    - 'Hub: um repo novo não é criado pelo agente: a primeira seção é "## 1. Manual" com a task [manual] …'
operations:
  apply:
    guidance:
      - "Hub: implemente cada task dentro de workspace/<repo>/, o clone do repo entre colchetes; nunca no próprio hub."
      - "Hub: siga a ordem do tasks.md; com uma task [manual] aberta, pare e peça ao usuário para concluí-la."
      - "Hub: não faça commit nos clones: o `hubspec hub pr <change>` faz isso na branch da change."

A escrita preserva o resto do arquivo:

  • no context, só o bloco entre os marcadores é substituído; o que estiver em volta fica;
  • nas listas, as entradas que começam com Hub: são substituídas, e as suas ficam antes delas;
  • as outras chaves e os comentários do YAML ficam como estão.

Implementação nos clones

  • Cada task é implementada dentro de workspace/<repo>/, na ordem do tasks.md.
  • Com uma task [manual] aberta antes, o agente para e pede que você a conclua.
  • Nenhum commit nos clones: as mudanças ficam no working tree até o hub pr.
  • Num repo com template: true, o agente segue a estrutura que o template criou e não recria pastas, pipelines nem infraestrutura.

Repo novo

O hub não cria repositórios. Quando a change precisa de um repo novo, a primeira seção é manual e bloqueia as outras:

## 1. Manual

- [ ] 1.1 [manual] Criar repo `boleto` via issue na automação da organização (bloqueia as demais)

## 2. boleto

- [ ] 2.1 [boleto] Emitir boleto — `src/`

O ciclo de uma change e o portão

A verificação guarda um retrato de cada clone e dos artefatos da change (Verificação entre repos). Dois passos do ciclo mudam esse retrato e fecham o portão:

  1. Applycódigo nos clones
  2. Verifyhubspec verify
  3. PRshub prmuda o retrato
  4. Mergena ordem, no GitHub
  5. Synchub syncmuda o retrato
  6. Verifysobre o código integrado
  7. Archivehubspec archive
  8. Docs e commithub document · commit no hub
  • hub pr grava → PR: <url> nas tasks: o hash dos artefatos muda.

$ hubspec gate add-pix
Portão fechado: o código ou os artefatos mudaram depois da verificação: verifique de novo

Na prática: verifique antes das PRs, para pegar falhas cedo, e de novo depois do merge e do sync. A segunda verificação é a que abre o portão, e o archive passa a registrar o estado integrado do sistema.

Hub multi-repo

Verificação entre repos

A verificação de uma change do hub é a mesma de um projeto único (Verificação e portão), com os testes rodando dentro dos clones. O comando roda na raiz do hub.

Membros

Quando há um repos.yaml na raiz, os membros da verificação são os repos ativos e clonados. Um repo sem clone não é membro, e um teste apontado para ele vira evidência inválida.

O trace

No hub, o hubspec scenarios <change> --template já inclui o campo repo em cada item. file é relativo à raiz do clone:

    { "id": "pix/Evento PixRecebido/QR code na tela", "kind": "manual", "note": "front ainda sem testes de UI" }

Execução

  • Cada teste roda com o diretório de trabalho no clone do repo, e o runner é detectado pelos arquivos desse clone (package.json, lockfile, pyproject.toml…).
  • O mesmo comando no mesmo clone roda uma vez só, mesmo que vários cenários apontem para ele.
  • O limite de tempo é de 5 minutos por teste (--timeout <s>).
$ hubspec verify add-pix --prove main
rodando: bun test ./src/events.test.ts -t publica PixRecebido
Veredito: CONCERNS
  #1 coberto, prova forte: Publica o evento
  #2 manual: QR code na tela
  #3 sem teste: tasks pendentes: 3.1

O retrato

O verification.json guarda uma chave por membro e uma para os artefatos:

"fingerprint": {
  "repo:api": "ca65952ed770…",
  "repo:worker": "44c15bae1cfb…",
  "repo:front": "a32768209b74…",
  "artifacts": "10ce591e7791…"
}
  • repo:<name> é o hash da árvore do working tree do clone: entram as mudanças não commitadas e os arquivos novos, e fica de fora o que está no .gitignore do repo. Commitar sem mudar conteúdo não muda o hash.
  • artifacts é o hash da pasta da change, sem o verification.md e o .hubspec/.
  • As docs do hub e o repos.yaml não entram: documentar não deixa a verificação desatualizada.
  • Clonar ou arquivar um repo muda o conjunto de chaves, e isso também deixa a verificação desatualizada.

A prova

Com --prove <commit-ish>, o mesmo commit-ish é resolvido em cada repo onde um teste passou. Use um nome que exista em todos, como a branch de trabalho: main, origin/main ou, num Git Flow, develop. A diferença em relação a um projeto único:

  • Projeto único: uma prova que não pode rodar (sem Git, código igual ao do commit) é erro do comando inteiro.
  • Hub: o problema fica registrado só no item daquele repo, como prova que falhou e o motivo, e os outros repos seguem.

Portão e archive

As regras do portão são as mesmas: verificação em dia, sem teste falhando, e cada item em CONCERNS conferido ou justificado. O hubspec archive <change> roda na raiz do hub e mescla as delta specs nas specs do sistema, em openspec/specs/ do hub. A ordem recomendada em relação às PRs está em O ciclo de uma change.

PRs coordenadas

hubspec hub pr <change> transforma as tasks concluídas de cada repo numa PR, na branch com o nome da change. Cada PR lista as PRs irmãs e a ordem de merge.

Pré-condições

Antes de mexer em qualquer clone, o comando lê o tasks.md e recusa a change inteira se:

CondiçãoMensagem
a change não tem tasks.mda change X não tem tasks.md
alguma task sem repohá tasks sem repo (2.3, …): toda task começa com [repo] ou [manual]
task [manual] abertaa task manual 1.1 ainda está aberta e bloqueia as demais: conclua-a (para um repo novo, `hubspec hub add <url> --new --change X`)
um título (depende de: …) cita um repo fora do manifestotasks.md declara "worker (depende de: lib)", mas lib não está no repos.yaml
tag de task que não está no manifestoo repo X não está no repos.yaml (repos: …)

Ordem de merge

  1. Os repos da change são os das tasks, sem manual, na ordem em que aparecem pela primeira vez no tasks.md.
  2. As dependências de cada repo são as do repos.yaml mais as declaradas nos títulos das seções da change.
  3. A ordem é a ordem de dependência (Kahn): empate pela ordem das tasks; num ciclo, o resto sai na ordem das tasks.

Rodar de novo

O comando é idempotente. Numa segunda execução, as PRs abertas são reaproveitadas, os repos cujas tasks foram concluídas no meio do caminho ganham a PR deles, e o corpo de todas é reescrito com a lista nova de irmãs. Um repo sem commits novos além da base fica pulado.

Chamadas ao gh

gh pr list --head <change> --state open --json url,number --limit 1procurar a PR aberta da branch
gh pr create --base <branch> --head <change> --title … --body …abrir a PR
gh pr edit <url> --body …reescrever o corpo com as irmãs

Rodam com GH_PROMPT_DISABLED=1 dentro de cada clone, então o gh resolve o repositório pelo remote do clone. Sem o gh instalado: o gh CLI não foi encontrado: instale-o e rode `gh auth login`.

Saída

Uma linha por repo, com o estado, o link e o detalhe, e a linha Ordem de merge: a → b → c quando há mais de uma PR. A saída é 0 mesmo com repos pulados, e 1 numa recusa ou num erro de Git ou do gh.

Nada no hub muda sozinho quando as PRs entram: o hubspec não recebe aviso do GitHub. Depois de um merge, a skill hubspec-hub sugere esses passos, nessa ordem.

Ciclo de vida dos repos

Registrar, alterar, ligar, aposentar e remover repos do manifesto, e o que cada operação faz com os clones e as docs.

hub add

hubspec hub add <url|dono/repo> [--name n] [--branch b] [--description t] [--tags a,b] [--depends a,b] [--new --change <change>]
  • Repo novo no manifesto: nome da URL ou de --name; branch de --branch, ou a do hub (conferida no remote, com aviso se faltar), ou a padrão do remote; path workspace/<name>.
  • Repo já registrado com a mesma URL: atualiza só o que foi informado. --branch e --description substituem; --tags soma às existentes; --depends acrescenta dependências manual.
  • Em ambos os casos, o repo fica active. Um hub add num repo arquivado o reativa; as docs antigas continuam em docs/archive/.
  • Os nomes de --depends precisam existir no manifesto.
  • Não clona: o clone vem no próximo hub sync, a não ser com --new.
  • Com --new --change: ver Repo novo.

hub depends

hubspec hub depends <repo> [--set a,b] [--add a,b] [--remove a,b] [--via <texto>] [--source llm|manual]

As operações são aplicadas nesta ordem: --set, --add, --remove.

OpçãoEfeito
--set a,bsubstitui a lista. Sem --via nem --source, uma dependência que já existia mantém os detalhes
--add a,bacrescenta; numa dependência que já existe, atualiza via e source se informados
--remove a,bremove
--via, --sourcevalem para as dependências de --set e --add; source padrão manual

Recusa autodependência e nomes fora do manifesto. A saída mostra a lista final, com [llm] nas dependências encontradas pelo agente:

$ hubspec hub depends worker --add api --via "evento PixRecebido" --source llm

hub archive

  • status: archived no manifesto; o repo continua listado.
  • docs/repos/<repo>/ vai para docs/archive/<repo>/, substituindo uma cópia anterior.
  • O clone fica no disco, mas o repo deixa de ser sincronizado, documentado e verificado.
  • No mapa, o repo vai para "Repos aposentados".
  • Repos ativos que ainda dependem dele recebem um aviso, mas as dependências não são mexidas:
$ hubspec hub archive api
atenção: worker, front, boleto ainda declara(m) dependência de api
  confira e, se for o caso, tire com: hubspec hub depends worker --remove api; hubspec hub depends front --remove api; hubspec hub depends boleto --remove api
api: arquivado (o sync deixa de cloná-lo; docs em docs/archive/api)

hub remove

Para um repo registrado por engano. Tira o repo do manifesto e apaga as docs e o clone.

  • Confirmação: --yes, ou a pergunta [s/N] num terminal interativo. Sem terminal e sem --yes, recusa.
  • Segurança: só apaga um clone que está dentro da pasta do hub. Recusa um clone com mudanças não commitadas ou com commits fora de qualquer remote, a não ser com --force.
  • O que apaga: docs/repos/<repo>/, docs/archive/<repo>/ e o clone. O manifesto é gravado por último, então uma execução interrompida termina na próxima.
  • Idempotente: um repo que não está no manifesto não é erro.
  • Os dependentes são avisados como no archive.
$ hubspec hub remove front --yes
hubspec: o clone tem mudanças não commitadas (workspace/front): envie ou descarte o trabalho, ou use --force

$ hubspec hub remove front --yes
front: removido do manifesto e das docs; clone workspace/front apagado

$ hubspec hub remove front --yes
front: não está no repos.yaml; nada a remover

Skills do hub

hubspec-hub

  • Orientação: lê o system-overview.md, depois overview, architecture e interfaces dos repos envolvidos. Só abre o código quando as docs não bastam, e nesse caso diz que a doc estava incompleta. Cita as docs em que se baseou.
  • Propor: uma change só no hub, pelo fluxo de sempre, com o tasks.md na gramática do hub e cenários que dizem onde cada comportamento acontece.
  • Implementar: em cada clone, na ordem; não passa de uma task [manual] aberta; não faz commit.
  • PRs: dry-run, confirmação, hub pr.
  • Depois do merge: status, sync, sugestão de atualizar as docs.

hubspec-document

  • Roda hub sync e hub document, e lê o .scan.json e o código de cada repo.
  • Escreve no nível intermediário: propósito, stack, componentes, uma linha por pasta relevante, fluxos, contratos de API e eventos, dependências. Não copia código e não documenta função por função.
  • Se baseia em fatos e diz o que é inferência; uma seção sem conteúdo leva "Não se aplica" e o motivo.
  • Registra as dependências com --source llm, e só remove uma manual com a sua confirmação.
  • Grava uma descrição de uma frase nos repos que estão sem, com hub add --description; não muda uma que já existe.
  • Preenche "O sistema" e "Fluxos entre repos" e roda --done. Não faz commit do hub sem pedido.

O que o agente não faz

  • descartar mudanças locais dos clones;
  • criar repositórios;
  • fazer commit nos clones (é o hub pr), ou no hub sem você pedir;
  • editar o trecho do mapa no system-overview.md;
  • abrir PRs sem mostrar o dry-run e pedir confirmação.

Perguntas

O hub clona a main ou a develop?

A branch de trabalho de cada repo: a branch do repo, senão a do hub (hub init --branch develop), senão a branch padrão do repositório no GitHub (detalhes). Num Git Flow, use develop (Git Flow).

Preciso informar as dependências entre os repos?

Não. O repos.md só lista os repos. Quando você pede "documente o hub", o agente encontra as dependências no código e as grava no repos.yaml com source: llm. Confira as marcadas com ¹ no mapa e registre com hub depends as que faltarem (detalhes). A descrição também é opcional: num repo sem ela, o agente escreve uma (detalhes).

Funciona com repositórios privados?

Sim, com a autenticação Git da máquina: chave SSH, ou gh auth setup-git para HTTPS. O hubspec nunca pede credenciais.

E GitLab, Bitbucket ou Azure DevOps?

O manifesto, o sync, a varredura, as docs, o status e a verificação usam só Git, sem a API do GitHub. O hub pr e a conversão de dono/repo dependem do gh e do GitHub. Outros provedores não foram testados.

Dá para checar as docs no CI?

Sim: hub status sai com 1 quando há docs desatualizadas ou faltando. O job precisa dos clones (hub sync) com credencial de leitura de cada repo.

hubspec check <change> <n> [--note] marca um item manual como conferido; hubspec justify <change> <n> <texto> justifica um item que causa CONCERNS (texto vazio remove a justificativa). Os dois aceitam o número (2 ou #2) ou o id do item, refazem o veredito e o relatório sem rodar testes, e saem com 0. As skills nunca os rodam por conta própria.

Prova vermelho → verde

Com --prove [commit] (padrão HEAD), cada teste que passou roda em duas cópias temporárias, extraídas com git archive, com as pastas de dependência (node_modules, .venv, venv) ligadas por link:

  • controle: o código de agora;
  • antes: o código do commit, com os testes de agora.

As notas são forte (passa no controle e falha antes), fraca (passa nos dois, o que deixa CONCERNS) e inconclusiva (falha no controle). Se o código não mudou desde o commit: o código não mudou desde HEAD: use --prove <commit de antes da change>.

Retrato e desatualização

O fingerprint tem duas partes:

  • código: num projeto Git, o hash da árvore do working tree, sem openspec/ e sem o que está no .gitignore, com as mudanças não commitadas; fora do Git, caminhos, tamanhos e datas;
  • artefatos: o conteúdo da pasta da change, sem verification.md e .hubspec/.

Qualquer diferença em relação ao retrato atual torna a verificação desatualizada. No hub, há uma chave de código por clone (detalhes).

Portão

hubspec gate <change> [--json] sai com 0 quando está liberado. Os motivos de fechamento são verificados nesta ordem:

sem verificaçãoverifique a change antes de arquivar: `hubspec verify X`
retrato mudouo código ou os artefatos mudaram depois da verificação: verifique de novo
FAILhá testes falhando: corrija e verifique de novo
CONCERNS sem justificativajustifique os itens que deixam o veredito em CONCERNS (#n, …) com `hubspec justify X <n> "<motivo>"`

O --json traz allowed, reason, verdict e missing, com os números dos itens que faltam. Um item manual conferido com check deixa de contar.

  • hubspec archive confere o portão e recusa com archive_gate_closed no --json; --no-gate arquiva sem verificação.
  • As skills /opsx:archive e /opsx:bulk-archive, que movem a pasta sem o CLI, rodam hubspec gate antes.
